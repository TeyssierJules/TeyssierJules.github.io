Entreprise Projet d'alternance présenté en soutenance 2026

Audit et durcissement Active Directory

  • Active Directory
  • PingCastle
  • GPO
  • Centreon

Contexte

Selon l'ANSSI, la santé fait partie des secteurs les plus exposés aux cyberattaques. J'ai monté un lab isolé qui reproduit l'Active Directory d'un client de ce secteur. Domaine sante-lab.local, contrôleur de domaine sous Windows Server 2019, virtualisé sous Proxmox.

Objectif

Mesurer le niveau de sécurité de l'Active Directory par un audit, le durcir selon les recommandations de l'ANSSI, vérifier le gain obtenu, puis surveiller le serveur.

Travail réalisé

  • J'ai introduit quatre vulnérabilités : SMBv1 actif, LLMNR actif, mots de passe de 7 caractères minimum, compte inactif ancien.admin.
  • J'ai audité l'annuaire avec PingCastle.
  • J'ai durci la configuration par GPO et PSO, selon l'ANSSI : SMBv1 et LLMNR désactivés, 14 caractères minimum pour tous, 15 pour les comptes à privilèges, ancien.admin désactivé.
  • J'ai relancé l'audit pour vérifier chaque correctif.
  • J'ai mis en place une supervision Centreon par SNMP : CPU, mémoire, disque, avec une alerte de test.

Résultat

J'ai contrôlé chaque correctif : SMBv1 et LLMNR désactivés, nouvelle politique de mots de passe appliquée, ancien.admin désactivé. Le niveau de risque a baissé.

On ne corrige pas à l'aveugle : avant de désactiver un compte, je vérifie à quoi il sert. Et un outil ne fait pas tout : les connecteurs Windows de Centreon demandaient une licence, j'ai configuré les indicateurs à la main.

Version publique : scores d'audit, organigramme et noms des personnes retirés.

BUT 2e année, en binôme Décembre 2025 – janvier 2026

Tests d'intrusion Six machines, de la reconnaissance à root

  • Kali Linux
  • nmap
  • Metasploit
  • DirBuster
  • zip2john
  • CVSS

Contexte

Un projet de 2e année, en binôme : six machines de labo volontairement vulnérables à attaquer depuis une Kali (Kioptrix, Blue, Academy, Blackpearl, Dev et Butler).

Objectif

Pour chaque machine : trouver une entrée, en prendre le contrôle, monter jusqu'aux droits administrateur, puis évaluer la gravité de la faille avec un score CVSS.

Travail réalisé

  • Kioptrix : Samba 2.2.1a repéré avec Metasploit, faille trans2open (CVE-2003-0201), shell root directement
  • Blue : Windows 7 vulnérable à EternalBlue (MS17-010), session avec les droits SYSTEM
  • Academy : FTP anonyme, mot de passe MD5 cassé, webshell PHP envoyé à la place d'une photo de profil, puis root grâce à un script planifié (cron) modifiable
  • Blackpearl : nom de domaine caché dans le code source, Navigate CMS 2.8 exploité, puis root grâce à PHP doté du bit SUID
  • Dev : partage NFS monté, archive protégée cassée avec zip2john, puis root grâce à un droit sudo sur zip
  • Butler : Jenkins avec ses identifiants par défaut, reverse shell en Groovy, puis SYSTEM avec PrintSpoofer (SeImpersonatePrivilege)

Résultat

Les six machines prises jusqu'aux droits administrateur (root ou SYSTEM). Chaque faille a son score CVSS, calculé à la main quand aucune fiche officielle n'existait.

La méthode est toujours la même : scanner, identifier les versions, chercher les failles connues. Quand je bloquais, c'était souvent sur un outil que je ne connaissais pas encore, comme Jenkins ou Nginx : il fallait d'abord comprendre comment il fonctionne.

La suite, cette année : Log4Shell et élévation de privilèges sur une autre plateforme de TP. Je l'ajouterai ici une fois terminée.

  • SNMP

  • Sigma

Contexte

Deux modules de 3e année. Le premier surveille le réseau, pour savoir ce qui tombe en panne. Le second surveille la sécurité, pour savoir ce qui se passe sur les machines. Tout est monté sur des machines virtuelles.

Objectif

Mettre en place une supervision complète : être alerté quand un équipement tombe en panne, et centraliser les journaux des machines pour pouvoir repérer un incident de sécurité.

Travail réalisé

  • Dimensionnement d'une plateforme Zabbix : bande passante sur le WAN, charge de la base (875 valeurs par seconde), stockage de l'historique (environ 190 Gio sur 30 jours)
  • Alertes sans « fatigue » : un seuil pour déclencher (90 %) et un autre pour revenir à la normale (70 %)
  • Installation de Zabbix 7.0 sur Debian, puis collecte par agent sur un serveur web et par SNMP v2c sur un routeur
  • Collecte des journaux Windows d'un contrôleur de domaine (Windows Event Forwarding, selon le guide de l'ANSSI), enrichis avec Sysmon
  • Centralisation des journaux Linux avec rsyslog, puis envoi des journaux Windows, Linux et Apache vers Splunk
  • Étude des règles de détection Sigma

Résultat

Les deux cibles répondent au serveur Zabbix, et les journaux Windows, Linux et Apache arrivent dans Splunk.

La plupart des blocages venaient de détails : une parenthèse oubliée, une majuscule dans un grep, trois fautes de syntaxe dans un fichier rsyslog, deux heures de décalage d'horloge entre deux machines. Je note maintenant chaque problème avec sa cause et sa correction.

BUT 2e année, en binôme Février – mars 2026

Sécurité des réseaux Attaquer, puis construire

  • Scapy
  • Wireshark
  • BIND 9
  • NGINX
  • OpenSSL

Contexte

Trois TP du module de sécurité des réseaux. Les deux premiers attaquent un réseau local, pour comprendre les failles d'ARP et du DNS. Le troisième construit une infrastructure web qui respecte un cahier des charges de sécurité.

Objectif

Comprendre deux attaques en les réalisant soi-même, puis construire une infrastructure qui respecte des règles de sécurité : tout en HTTPS, aucune erreur de certificat, des serveurs joignables uniquement par le frontend.

Travail réalisé

  • Empoisonnement de cache ARP avec Scapy : fausses requêtes puis fausses réponses ARP, pour que la victime envoie ses paquets à l'attaquant. Vérifié dans Wireshark et dans la table ARP
  • Serveur DNS BIND configuré comme autorité d'un domaine de test
  • Empoisonnement DNS : les requêtes DNS ne passent pas par l'attaquant, donc il les détourne d'abord par ARP, puis répond avant le vrai serveur avec une fausse adresse. Ensuite, empoisonnement du cache du serveur DNS lui-même
  • Reverse proxy NGINX : un frontend relié à deux réseaux, trois serveurs en backend (dont un en HTTPS), répartition de charge, tout redirigé vers HTTPS
  • Autorité de certification locale avec OpenSSL, ajoutée au client : aucune erreur de certificat

Résultat

Les deux attaques fonctionnent. La victime envoie son trafic à l'attaquant, et sa requête DNS reçoit la fausse adresse choisie : dig répond 172.25.0.27 au lieu de 172.25.0.28.

ARP et le DNS croient la première réponse qui arrive, sans rien vérifier. Il nous a suffi de désactiver DNSSEC pour que l'attaque marche : c'est pour ça qu'il compte.

Perso Prototype Juillet 2026

Lien Santé Bracelet QR pour résidents

  • Node.js
  • Fastify
  • React (PWA)
  • SQLite
  • AES-256-GCM

Contexte

L'idée : un bracelet avec un QR pour les résidents d'EHPAD ou d'hôpital. Une personne qui le scanne voit qui est le résident et qui prévenir. Le personnel crée et met à jour les fiches. Ce sont des données de santé, donc la sécurité devait être pensée dès le départ.

Objectif

Concevoir un système où le QR ne révèle rien à lui seul et où les données médicales sont protégées, puis prouver avec un prototype que la boucle fonctionne : créer une fiche, générer le QR, le scanner, lire la fiche.

Travail réalisé

  • Cahier des charges, modèle de données et maquettes des écrans
  • Aucune donnée lisible dans le QR : il ne contient qu'un identifiant opaque, que l'on peut régénérer si un bracelet est perdu
  • Données médicales chiffrées au repos (AES-256-GCM), journal de chaque scan, fiche désactivable
  • Prototype : API Node.js (Fastify), application web installable (PWA React) avec scanner intégré, base SQLite, impression du QR
  • Données fictives uniquement

Résultat

Le prototype tourne : créer une fiche, générer le QR, le scanner avec un téléphone, lire la fiche. Il n'a pas été déployé.

Le cahier des charges prévoyait deux vues : une vue publique pour le passant, et la fiche médicale pour un soignant connecté (Keycloak, droits par rôle). Le prototype est plus simple : tout le monde voit la fiche, et la connexion, simulée, ne sert qu'à la modifier.

Sur des données de santé, la sécurité se décide avant le code : qui voit quoi, ce qu'on chiffre, ce qu'on garde en trace. Et sur téléphone, sans HTTPS, le navigateur bloque la caméra : il a fallu le prévoir dès le départ.

MonCoffreFort Coffre-fort numérique

  • Java
  • Android
  • SQLite
  • SHA-256

Contexte

Projet du module de programmation Java. Je l'ai réalisé seul, en autonomie. Il se terminait par un examen.

Objectif

Développer une application Android qui protège des documents sensibles : accès par code, récupération en cas d'oubli, et une base de données à l'abri des injections SQL.

Application terminée et présentée à l'examen de Java.

SHA-256 seul ne suffit pas pour protéger un PIN court. Aujourd'hui, j'utiliserais un algorithme lent avec un sel, comme bcrypt ou Argon2.

Je voulais piloter tous les objets connectés de mon logement depuis un seul serveur, sans passer par l'application de chaque marque.

Objectif

Un serveur qui réunit tous les appareils, quelle que soit leur marque, avec des automatisations utiles au quotidien : lumières, qualité de l'air, commande vocale.

Travail réalisé

  • Installation de Home Assistant OS sur un mini PC reconditionné (Lenovo ThinkCentre M700 Tiny)
  • Réseau Thread avec une clé ZBT-2 comme routeur de bordure, appairage des appareils en Matter
  • Ampoules IKEA pilotées par télécommande dans chaque pièce, via un blueprint et un script ajouté à la main
  • Capteur de qualité de l'air, avec alertes sur mon téléphone si le CO₂ dépasse 1000 ppm ou si les particules fines montent
  • Commande vocale avec Alexa, accès à distance avec Nabu Casa

Résultat

Les lumières se pilotent à la télécommande, à la voix ou depuis le téléphone. La qualité de l'air est surveillée en continu.

Prochaines étapes : aquarium connecté, audio multiroom.

Deux appareils avec le même nom suffisent à casser une automatisation. Maintenant, je nomme chaque appareil de façon unique avant de le configurer.
