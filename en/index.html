Work Work-study project presented to a jury 2026

Active Directory audit and hardening

  • Active Directory
  • PingCastle
  • GPO
  • Centreon

Context

According to ANSSI, the French national cybersecurity agency, healthcare is one of the sectors most exposed to cyberattacks. I built an isolated lab that reproduces the Active Directory of a client in this sector. Domain sante-lab.local, domain controller on Windows Server 2019, virtualised on Proxmox.

Objective

Measure the security level of the Active Directory with an audit, harden it following ANSSI guidelines, check the improvement, then monitor the server.

Work done

  • I introduced four vulnerabilities: SMBv1 enabled, LLMNR enabled, 7-character minimum passwords, an inactive account named ancien.admin.
  • I audited the directory with PingCastle.
  • I hardened the configuration with GPOs and PSOs, following ANSSI guidelines: SMBv1 and LLMNR disabled, 14-character minimum for all users, 15 for privileged accounts, ancien.admin disabled.
  • I ran the audit again to check each fix.
  • I set up Centreon monitoring over SNMP: CPU, memory, disk, with a test alert.

Outcome

I checked every fix: SMBv1 and LLMNR disabled, new password policy applied, ancien.admin disabled. The risk level went down.

You don't fix things blindly: before disabling an account, I check what it's used for. And a tool doesn't do everything: Centreon's Windows connectors required a licence, so I configured the metrics by hand.

Public version, in French: audit scores, org chart and people's names removed.

Penetration testing Six machines, from reconnaissance to root

  • Kali Linux
  • nmap
  • Metasploit
  • DirBuster
  • zip2john
  • CVSS

Context

A year-2 project, in pairs: six deliberately vulnerable lab machines to attack from Kali (Kioptrix, Blue, Academy, Blackpearl, Dev and Butler).

Objective

For each machine: find a way in, take control, escalate to administrator rights, then rate the severity of the flaw with a CVSS score.

Work done

  • Kioptrix: Samba 2.2.1a identified with Metasploit, trans2open flaw (CVE-2003-0201), root shell straight away
  • Blue: Windows 7 vulnerable to EternalBlue (MS17-010), session with SYSTEM rights
  • Academy: anonymous FTP, MD5 password cracked, PHP webshell uploaded as a profile picture, then root through a writable scheduled script (cron)
  • Blackpearl: domain name hidden in the page source, Navigate CMS 2.8 exploited, then root through PHP with the SUID bit
  • Dev: NFS share mounted, protected archive cracked with zip2john, then root through a sudo right on zip
  • Butler: Jenkins with its default credentials, reverse shell in Groovy, then SYSTEM with PrintSpoofer (SeImpersonatePrivilege)

Result

All six machines taken up to administrator rights (root or SYSTEM). Each flaw has its CVSS score, calculated by hand when no official record existed.

The method is always the same: scan, identify versions, look for known flaws. When I got stuck, it was often on a tool I didn't know yet, like Jenkins or Nginx: I first had to understand how it works.

University Year 2, in pairs February – March 2026

Network security Attack, then build

  • Scapy
  • Wireshark
  • BIND 9
  • NGINX
  • OpenSSL

Context

Three labs from the network security module. The first two attack a local network, to understand the weaknesses of ARP and DNS. The third one builds a web infrastructure that meets a set of security requirements.

Objective

Understand two attacks by carrying them out, then build an infrastructure that follows security rules: everything in HTTPS, no certificate errors, servers reachable only through the frontend.

Work done

  • ARP cache poisoning with Scapy: forged ARP requests, then forged replies, so the victim sends its packets to the attacker. Checked in Wireshark and in the ARP table
  • BIND DNS server set up as the authority for a test domain
  • DNS poisoning: DNS queries do not go through the attacker, so he first redirects them with ARP, then answers before the real server with a fake address. Then, poisoning the cache of the DNS server itself
  • NGINX reverse proxy: a frontend on two networks, three backend servers (one in HTTPS), load balancing, everything redirected to HTTPS
  • Local certificate authority with OpenSSL, added to the client: no certificate errors

Result

Both attacks work. The victim sends its traffic to the attacker, and its DNS query gets the fake address: dig returns 172.25.0.27 instead of 172.25.0.28.

ARP and DNS trust the first answer that arrives, without checking anything. We only had to disable DNSSEC for the attack to work: that is why it matters.

Personal Prototype July 2026

Lien Santé A QR wristband for residents

  • Node.js
  • Fastify
  • React (PWA)
  • SQLite
  • AES-256-GCM

Context

The idea: a wristband with a QR code for residents of care homes or hospitals. Anyone who scans it sees who the resident is and who to call. Staff create and update the records. This is health data, so security had to be designed in from the start.

Objective

Design a system where the QR code reveals nothing on its own and medical data is protected, then prove with a prototype that the loop works: create a record, generate the QR code, scan it, read the record.

Work done

  • Requirements, data model and screen mock-ups
  • No readable data in the QR code: it only holds an opaque identifier, which can be regenerated if a wristband is lost
  • Medical data encrypted at rest (AES-256-GCM), every scan logged, records can be deactivated
  • Prototype: Node.js API (Fastify), installable web app (React PWA) with a built-in scanner, SQLite database, QR printing
  • Fictional data only

Result

The prototype works: create a record, generate the QR code, scan it with a phone, read the record. It has not been deployed.

The requirements planned two views: a public one for passers-by, and the medical record for logged-in staff (Keycloak, role-based access). The prototype is simpler: everyone sees the record, and the login, simulated, is only used to edit it.

With health data, security is decided before the code: who sees what, what gets encrypted, what gets logged. And on a phone, without HTTPS, the browser blocks the camera: this had to be planned from the start.
